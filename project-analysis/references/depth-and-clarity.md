# 分析深度与通俗表达

## 目标

让业务人员知道“它做什么、什么时候成功或失败”，让开发人员知道“在哪里决定、如何验证、变更影响什么”，让维护人员知道“出故障后哪些数据和外部效果需要处理”。篇幅长、图多、术语多，都不代表分析深入。

## 每个功能的调查闭环

1. **建立问题**：从真实入口出发，写下参与者、输入、用户期望结果和当前待证实的行为。入口包括页面、API、命令、事件、定时任务和数据库例程。
2. **定位决定点**：穿过转发层、接口、装饰器、中间件和仓储封装，找到实际权限判断、条件分支、计算、字段赋值、状态变更和副作用。遇到动态注册，核对依赖注入、插件、生成代码及环境配置。
3. **还原规则**：记录原始条件、求值顺序、空值/边界值、单位、金额精度、时区和默认值。中文解释要保留条件的严格含义，例如 `>` 不得解释成“大于等于”。
4. **连起结果**：从决定点追到响应、页面变化、持久化、消息、文件或外部调用，再反向核对消费者和读取方。找不到的边界写入缺口，不画想象中的箭头。
5. **检验另一种解释**：例如“重试不会重复创建”也可能只在单进程成立；检查唯一约束、事务隔离和并发入口，而非仅看到一段查询就认定幂等。记录能推翻结论的最小安全检查。
6. **用证据闭环**：核对实现与已有测试、配置、契约或结构元数据。可安全运行且获授权时执行窄测试；不能执行时做静态检查并明确“未运行”。不能为完成分析修改被分析的产品源码。
7. **立即归档**：更新功能、分支、字段、关系、证据、图示和缺口。完成一个模块就对账一个模块，不能先写漂亮总论，再补猜测细节。

## 必须问清的技术问题

| 主题 | 需要回答 | 不足以支撑结论的线索 |
| --- | --- | --- |
| 权限 | 在哪里执行，哪个身份/租户参与，所有入口是否一致 | 前端隐藏按钮 |
| 幂等/并发 | 去重键及作用域、原子性、过期、竞争时结果 | 函数名叫 `safeCreate` |
| 事务 | 哪些写入同事务，哪些外部效果不在事务里 | 外层出现 `transaction` |
| 异步 | 发布与提交顺序、重复/乱序、失败重试、死信与重放 | 两个节点间画一条箭头 |
| 数据 | 当前有效结构、全部字段、真实连接列、读写者、删除及归档 | 历史建表语句或 ORM 名称 |
| 缓存 | 键/租户隔离、有效期、失效时机、读写一致性 | 引用了 Redis 客户端 |
| 性能 | 输入规模、查询/调用次数、实际索引及成本证据 | 有索引就声称查询快速 |
| 发布 | 实际构建目标、环境选择、配置覆盖、迁移先后和回滚限制 | 单个 Dockerfile |

逐项覆盖真实适用问题；不适用也需说明理由。高风险功能增加证据深度，但不能只分析高风险功能。

## 三层阅读结构

**第一层：业务概览。** 用三至五句中文解释系统服务谁、解决什么问题、核心输入与输出、外部依赖及分析范围。只概括已完成调查的事实。

**第二层：功能讲解。** 每个功能先讲“谁在什么情况下做什么、系统如何判断、最后得到什么”，再给成功示例和失败示例。流程图使用“检查库存是否足够”这类动宾短句，不能只堆 `Controller -> Service -> DAO`。

**第三层：实现证据。** 展开后查看具体接口、函数、条件、字段、表关系、事务边界、错误码、测试和源码定位。三层共用对象 ID；通俗摘要不得隐藏与技术详情矛盾的事实。

表说明需要讲清“一行代表什么”“主键如何标识它”“哪些字段决定业务状态”“它与其他表为什么关联”。字段说明保留技术原名，并解释业务含义、来源、单位、取值范围、空值含义和使用方；不能把未知业务含义编成中文注释。

## 结构化讲解契约

`feature`、`api`、`table`、`job` 实体必须带 `explanation` 对象，报告在技术详情之前展示。以下字段使用中文，代码标识保持原名：

```json
{
  "explanation": {
    "purpose": "这个功能解决什么问题；对于表，说明一行代表什么。",
    "howItWorks": ["参与者提供什么输入", "在哪些条件下发生哪些操作", "最后返回或改变什么"],
    "example": "说明性假设示例，不是真实用户数据或已执行测试。",
    "failure": "失败条件、用户能看到的结果、已写数据和外部效果如何处理。",
    "boundaries": "已证实的适用范围，以及不能从现有证据得出的结论。",
    "terms": [{"term": "幂等", "meaning": "同一业务请求重复执行时，不应重复产生同一业务结果；具体保障以实现为准。"}],
    "evidence": ["证据ID"]
  }
}
```

没有专有术语可用空 `terms`；其他字段不能是空白。`howItWorks` 必须包含可读步骤而非函数名列表。运行库缺失、异常结果未核实等情况可以诚实说明，但相关实体/缺口不得因此自动标为已核实。

## 表达规则

- 先讲业务结果，再给实现路径；先给结论，再给证据和限制。
- 一个句子讲一个主要因果，少用“赋能、闭环、健壮、解耦”等没有具体说明的评价词。
- 第一次出现术语时给一句解释，例如“死信队列：多次处理失败后暂存消息的地方”。
- 示例必须标注“说明性假设”，不得伪装成生产数据、测试结果或实际性能数据。
- 分开写“代码实际做了什么”“资料记载的设计意图”“分析者推断”“改进建议”。没有意图证据就写“无法确认设计动机”。
- 不为了通俗隐藏错误分支、精度、权限范围或事务限制；让例子与源码条件逐项对应。
- 图必须附一句业务解释、边的含义和证据入口；图与正文矛盾时先修正事实。

## 验收门槛

三类门槛单独出结论，不取平均分，不用某一项通过掩盖另一项未通过。

**深度门槛**：每个功能都能定位决定行为的实现，说明关键条件与后果，覆盖适用的异常/权限/事务/并发边界；结论有反向或独立来源核对。仅登记路由或读 README 不通过。

**覆盖门槛**：原始发现清单与报告逐 ID 对账，每个仓库及领域都完成处置，字段、关系、图示和分支没有静默丢失。未知、排除、受阻分别记录。

**易懂门槛**：从报告自身能回答“谁使用、做什么、何时拒绝、改变哪些数据、出了问题怎么办、证据在哪里”。每个关键对象有中文讲解，术语有解释，示例不引入新事实。由 Agent 检查只能记为“自查”；没有真实读者反馈，不得宣称“用户理解测试通过”。

在 `checks` 记录实际审阅范围、对象 ID、检查方法、结果及证据。无法回答的问题进入 `gaps`，由下一次调查解决，不能改成含糊总结。

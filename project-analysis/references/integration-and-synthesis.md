# 跨系统整合与业务全貌

## 目的与优先级

联合分析不是分别介绍前端、后端、数据库后再拼接文档，而是还原同一项业务在不同实现之间如何完成。优先保证事实、整合、完整性与中文可理解性；桌面 HTML 是承载这些结论的工具，手机适配仅保持基本可用。

先回答六个问题：谁发起、谁做决定、信息如何转换、数据由谁负责、何时算完成、失败后还有哪些效果存在。能列出仓库和函数名，但回答不了这些问题，不算整合完成。

## 1. 建立统一概念，不合并原始证据

- 为仓库、模块、环境、版本分别建立身份；同名文件、函数、表不得跨仓库直接去重。
- 为业务概念建立中文名称、原始术语、实体 ID、适用范围和映射依据。例如页面中的“客户”和某表中的 `account` 是否是同一概念，要验证标识来源、租户范围及读写关系。
- 同一业务能力可以关联多个实现 ID；同一函数也可以服务多个业务能力。前端 DTO、接口字段和数据库列不是同一种对象，保留独立记录并注明转换关系。
- 枚举值、金额单位、时区、精度、空值含义、默认值与 ID 格式必须逐项对齐。不同语言的数据类型名称相近，并不代表序列化与业务语义相同。
- 生成代码、接口声明、适配器和实际运行实现分开登记。映射只有静态证据时，不得称为已观测运行路径。

概念映射可保存在 `sections.architecture.details.concepts` 对应章节记录的 `details.concepts` 中，每项带 `name`、`aliases`、`entities`、`scope`、`evidence`。这里的 `sections.architecture` 是章节 ID 的简称，实际 `sections` 仍是数组。扩展字段由执行 Agent 校核，不是校验器自动识别出的事实。

## 2. 双向核对每个系统边界

先从调用方提取完整请求集合，再从接收方独立提取入口集合，保存独立发现结果。比较两边集合，未匹配记录需要区分无消费者入口、外部系统、版本差异、动态入口、废弃功能和证据不足；不允许只处理成功匹配的交集。

| 核对维度 | 需要验证的两端事实 |
| --- | --- |
| identity | HTTP 方法、基础地址、网关改写、版本和路径；或消息通道/操作名/任务绑定/FFI 符号 |
| payload | 输入字段及来源、必填性、序列化、类型、单位、精度、枚举、空值及字段转换 |
| authorization | 身份如何传递，角色/权限/租户在哪一层检查，代理与消费者身份是否变化 |
| outcome | 返回码和结构、页面如何消费、异步确认与最终业务成功的区别 |
| failure | 错误类型、超时、重试/取消、重复/乱序、死信、部分成功、补偿后的用户结果 |
| consistency | 事务边界、提交与发布顺序、幂等范围、缓存更新、读写可见性和外部效果 |

HTTP、消息、文件交换、ETL、共享数据库和 FFI 按各自语义解释这些维度。不存在的维度写 `not-applicable` 并保留两端核查和理由，不能为凑字段虚构权限、返回码或事务。

跨仓库关系必须有 `contract`；同仓库的跨进程、网络、消息或独立存储边界标记 `boundary: true`，同样要求契约。`producer` 指关系 `from` 端的行为，`consumer` 指 `to` 端的行为，不以函数名称推断真实生产消费角色。反向关系需交换两端记录。

## 3. 契约记录与机器门槛

在既有 `relations` 记录中增加 `contract`，不创建一套脱离业务对象的孤立报告。以下示意只展示一个维度，实际必须包含上表六个维度：

```json
{
  "id": "REL-WEB-API",
  "from": "WEB-CHECKOUT",
  "to": "API-CREATE",
  "kind": "HTTP_CALLS",
  "label": "提交订单",
  "status": "verified",
  "evidence": ["EV-WEB", "EV-API"],
  "boundary": true,
  "contract": {
    "environment": "仅已核实的测试环境配置，不代表生产环境",
    "versionContext": "对应双方清单中的版本快照及网关配置版本",
    "producerEvidence": ["EV-WEB"],
    "consumerEvidence": ["EV-API"],
    "dimensions": {
      "payload": {
        "producer": "发送整数金额，单位为分",
        "consumer": "按整数分解析并存储",
        "status": "compatible",
        "reason": "调用方构造字段与接收方解析、赋值规则一致",
        "evidence": ["EV-WEB", "EV-API"]
      }
    }
  }
}
```

维度状态为 `compatible`、`mismatch`、`unknown` 或 `not-applicable`。双方观察、判断依据和证据不能为空。源码证据必须属于相应端仓库；部署清单、元数据等产物证据还需人工验证其归属和版本。

校验器检查必要字段、两端源码证据归属、引用和状态，不会自动推导协议兼容性，也不会判断一段中文是否真实。禁止把双方都填成“已检查”或复制同一摘要以通过门槛。

### 兼容性与分析完成度分开

已证实的缺陷也是分析结果。`mismatch` 维度必须用 `finding` 引用一个 `kind: risk`、`status: verified` 的实体，风险需带证据和 `details.businessImpact`，说明实际业务后果。结构校验通过后，该不兼容仍保留在报告限制清单中；不能改成 `compatible`，也不代表产品缺陷已修复。

未核实的冲突或没有业务后果说明的冲突阻止整合完成。访问不到对端时保留 `unknown`，建立开放缺口并说明需要什么证据，不能用调用方的假设填充对端。

## 4. 沿一项业务完成因果整合

每项业务保留完整且有证据的路径：入口 → 身份与参数 → 决定条件 → 数据转换 → 事务/持久化 → 异步及外部效果 → 用户结果。路径根据真实项目裁剪；CLI、库、移动端或 ETL 不得强行套入 Web 架构。

除了成功路径，还要说明关键分支在何处改变结果：权限拒绝前后有无写入、事务失败时哪些写入回滚、超时是否可能已完成、重试会否重复、通知失败是否影响主业务、数据延迟是否被用户感知。局部成功不能替代端到端成功，例如返回“已受理”不等于实际处理结束。

在原有功能 `explanation` 中形成连贯中文讲解，在 `details.integration` 保留各节点 ID、数据变化、边界与分支来源。关联信息引用现有 ID，不重复复制易过期的字段字典。正文、图示、字段、风险和证据必须使用同一组事实。

## 5. 冲突裁决与数据所有权

不要机械规定“源码永远优于文档”或“运行库永远优于迁移”。先确认它们回答的是哪个环境、版本、时间和对象，再比较：设计文档解释意图；配置选择实现；源码说明静态行为；测试只证明其覆盖场景；运行证据说明观测到的执行；数据库元数据说明那个实例当时的结构。

冲突记录需保留双方结论与证据、涉及的环境版本、受影响的功能/字段/链路、业务后果、当前判断和下一项最小核查。无法裁决就保留冲突，不把差异润色成共同结论。

数据分析还要区分事实来源表、读模型、缓存、报表、副本与归档。逐项说明谁创建、谁修改、谁消费、何时同步、如何删除；共享数据库和定时 ETL 也可能是系统连接，不能只扫描 HTTP 调用。表有相似字段不等于有物理外键，代码 JOIN 不等于运行库约束。

## 6. 全局收敛，不只局部总结

1. 按模块完成调查并即时保存；再按业务能力聚合，列出跨仓库和跨语言边界，不丢掉底层模块的独有功能。
2. 从入口顺向追踪，再从持久化、输出、消息消费者反向找来源，检查孤立节点和隐含的共享状态。
3. 用独立候选集合核对所有根目录和领域；为每个集合保存 `checks.expectedIds`、`observedIds`、完整分页情况及证据。计数相同不代表集合一致。
4. 对重点问题做组合核查：前端是否会走到后端允许的分支，字段是否能承接真实值，重试是否跨越非幂等副作用，回滚是否真的包括外部系统。
5. 完成跨模块去重、别名映射、冲突登记后，才写系统总论。总论必须解释协作方式、主要数据所有权、关键规则、失败模式和未知边界，不只是列技术栈。
6. 报告变更影响时列出证据支持的关系路径和需要重查的契约/字段/测试。静态可达仅是潜在影响，不是已发生故障；版本变化只重用仍有效的证据，刷新受影响结论。

## 7. 整合验收与质量边界

在 `checks` 中单列“整合自查”，记录业务能力范围、实际核查对象和结果；与深度、覆盖、易懂性分开报告，不取平均分。

通过条件：每个边界有双方核对，未匹配项有处置，环境/版本没有混用，字段转换与事务限制可追溯，冲突有证据和业务影响，读者能从一个业务入口找到全过程及失败后果。

测试应覆盖同名跨仓库对象、字段单位冲突、缺少对端证据、版本错配、异步部分失败和不可访问依赖等场景。单元样例用于验证防错门槛；真实分析能力仍需在获授权的实际项目上检验。不能把样例测试通过宣传为“任何项目都能完美分析”。
